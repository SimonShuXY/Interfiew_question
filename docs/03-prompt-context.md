# 03. 提示词与上下文工程

上一章解释了 LLM 如何根据上下文生成输出。本章要解决的问题是：如何把任务、规则、资料、工具和状态组织成模型能可靠使用的上下文。

本章目标：从“写提示词”升级到“设计上下文契约”。
下一章：当上下文不足以解决问题时，引入工具调用。

## 从提示词到上下文工程

提示词不是一句神奇咒语，而是模型执行任务的接口说明。上下文工程包括：

- 任务目标。
- 角色和责任边界。
- 输入数据。
- 可用工具。
- 输出格式。
- 约束和禁止事项。
- 示例。
- 业务规则。
- 历史状态。
- 当前环境反馈。

好的上下文像一份清晰的工作单：让模型知道目标、材料、限制、完成标准和失败时该怎么做。

## 指令分层

常见上下文可以按优先级分层：

| 层级 | 内容 | 例子 |
| --- | --- | --- |
| 系统层 | 长期身份、安全边界 | “你是企业内部知识助手，不得泄露无权限资料” |
| 开发者层 | 应用规则、流程、工具策略 | “需要实时数据时先调用 search_docs” |
| 用户层 | 当前需求 | “帮我总结这份合同的风险” |
| 数据层 | 文档、检索片段、工具结果 | 合同文本、数据库记录 |
| 输出层 | 格式和验收标准 | JSON schema、报告模板 |

如果规则之间冲突，要让更高层规则明确胜出。不要把核心规则散落在长文档中。

## 写给 Agent 的任务指令

Agent 指令要比普通聊天提示更明确，因为它会行动。建议至少包含：

```text
目标：你要完成什么。
边界：你不能做什么。
工具策略：什么时候用哪个工具，什么时候不要用。
失败策略：缺信息、工具失败、权限不足时如何处理。
输出格式：最终结果必须满足什么 schema 或模板。
质量标准：什么叫完成，什么叫需要继续。
```

示例：

```text
你是订单售后 Agent。你的目标是根据用户诉求、订单状态和售后政策给出处理结果。
如果需要订单信息，调用 get_order。
如果用户要求退款，必须先调用 check_refund_policy。
任何真实退款动作必须调用 request_human_approval，审批通过后才能调用 issue_refund。
如果订单号缺失，先向用户询问，不要猜测。
最终输出必须包含 decision、reason、next_action 三个字段。
```

## 上下文预算

Agent 常见上下文来源很多，但不是都该塞进模型。

优先放入：

- 当前目标。
- 最近关键对话。
- 已确认事实。
- 工具返回的最新结果。
- 与当前步骤强相关的资料片段。
- 输出格式和安全边界。

谨慎放入：

- 大量历史对话。
- 未筛选网页。
- 用户上传的长文档全文。
- 工具返回的调试日志。
- 与当前任务无关的记忆。

不要让模型在一堆无关文本里找关键规则。上下文越乱，Agent 越像在猜。

## 示例的作用

示例可以显著提升稳定性，尤其是：

- 输出格式复杂。
- 工具选择容易混淆。
- 业务规则有边界情况。
- 需要固定语气或报告结构。

示例应覆盖正例和反例。反例尤其重要，例如“没有订单号时不要调用退款工具”。

## 状态摘要

多轮 Agent 不能无限携带完整历史。状态摘要应记录：

- 用户目标。
- 已完成步骤。
- 已获取事实。
- 未解决问题。
- 工具调用结果。
- 当前决策依据。
- 下一步候选动作。

状态摘要不是普通聊天总结，而是任务执行状态。它要服务下一步行动。

## 常见误区

- 把所有业务文档原样塞进 prompt，不做拆分和检索。
- 只写角色，不写完成标准。
- 只写“认真、准确”，不写可验证规则。
- 工具说明过短，导致模型不知道何时调用。
- 输出格式没有 schema，后续程序只能脆弱解析自然语言。
