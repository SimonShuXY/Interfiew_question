01. Agent 是什么¶

上一章确定了学习方法。现在要先清理概念边界：不是所有接入 LLM 的应用都是 Agent。如果这个边界不清楚，后面选工具、做架构、做评测都会变形。

本章目标：理解 Agent 的组成、层级和难点。 下一章：回到 Agent 的核心发动机，也就是 LLM 的基础能力和限制。

一句话定义¶

Agent 是一个由 LLM 驱动的系统，它能围绕目标读取上下文、做决策、调用工具、观察结果，并在循环中推进任务，直到完成、失败、需要人工介入或触发停止条件。

一个更工程化的定义是：

Agent = Model + Instructions + State + Tools + Control Loop + Guardrails

这里的关键不是“能聊天”，而是“能控制执行过程”。普通聊天模型只生成回答；Agent 会决定下一步是否查资料、调用 API、写文件、请求确认、重试或停止。

Agent 与相邻概念¶

类型 主要特征 是否是 Agent
单轮 LLM 调用 输入问题，模型直接回答 通常不是
聊天机器人 多轮对话，但不控制工具执行 通常不是
RAG 问答 检索资料后回答 不一定是
固定工作流 代码预先决定每一步 是 agentic workflow，但不一定是自主 Agent
工具调用 LLM 模型能选择函数或 API 接近 Agent
Agent 模型在循环中动态选择步骤和工具 是
多 Agent 系统 多个 Agent 分工协作或交接 是，但更复杂

Agent 的最小组成¶

一个可运行 Agent 至少需要五件事：

组成 作用 例子
目标 告诉系统要完成什么 “分析这份合同风险并输出报告”
模型 负责理解、推理、决策、生成 GPT、Claude、Gemini、本地模型
指令 约束模型行为 角色、任务步骤、禁止事项、输出格式
工具 让模型能影响外部世界 搜索、数据库、邮件、代码执行、支付系统
状态 记录当前进度和上下文 对话历史、任务状态、工具结果、记忆

生产系统还必须有护栏、日志、评测、权限、成本控制和人工介入。

Agent 能力分层¶

可以把 Agent 能力分成 5 个层级：

层级 能力 典型形态
L0 文本生成 提示词问答、总结、改写
L1 结构化输出 JSON、表格、分类、抽取
L2 工具使用 函数调用、API 查询、数据库检索
L3 循环执行 多步工具调用、观察结果、动态重试
L4 协作执行 多 Agent、远程 Agent、人工协作、长期任务

0 基础学习者常见问题是跳过 L0-L2，直接追 L4 多 Agent。这样通常会得到一个复杂、昂贵、不可控的系统。正确路线是先把单 Agent 做可靠，再扩展协作。

Agent 的核心循环¶

最小 Agent 循环可以写成：

while not done:
    read goal, state, available tools
    model decides next action
    if action is final answer:
        return answer
    if action is tool call:
        validate permission and arguments
        execute tool
        store observation
    if blocked or unsafe:
        ask human or stop

这个循环解释了为什么 Agent 比普通 LLM 应用难：每一轮都可能累积错误、产生副作用、消耗成本或暴露数据。

什么时候不该做 Agent¶

以下情况优先用普通代码或固定工作流：

  • 规则清晰、输入格式稳定、输出可用确定性代码生成。
  • 任务只需要一次模型调用。
  • 工具调用有高风险，但没有人工确认和回滚机制。
  • 无法定义成功标准，也没有评测数据。
  • 低延迟、低成本要求极高，而 Agent 需要多轮推理和工具调用。

一个实用原则：如果你能用函数稳定解决，就先写函数；只有当输入复杂、规则难维护、需要模型动态判断时，再引入 Agent。

常见误区¶

  • 把“多提示词链路”都叫 Agent。固定步骤更准确地说是工作流。
  • 以为多 Agent 天然更强。多 Agent 会增加通信成本、上下文丢失和调试难度。
  • 只优化提示词，不优化工具。工具名称、参数、错误信息和权限边界会直接影响 Agent 能力。
  • 没有停止条件。没有最大轮数、预算和失败策略的 Agent 容易循环、乱调用工具或无限消耗。

本章练习¶

判断下面场景应该用什么形态，并说明理由：

  1. 输入用户评论，输出情感分类。
  2. 查询公司知识库，回答员工报销制度。
  3. 根据用户邮件、订单状态和退款政策判断是否退款，并必要时发起退款。
  4. 让系统在一个代码仓库中定位 bug、修改代码、运行测试、提交修复建议。

下一章会解释 LLM 为什么能作为 Agent 的“大脑”，以及为什么它不能被当成可靠的普通函数。
