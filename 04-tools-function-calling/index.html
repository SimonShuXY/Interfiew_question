04. 工具调用与 MCP¶

上一章解决了“模型应该看到什么”。但很多任务不能靠上下文完成，因为模型需要实时数据、私有数据、计算能力或外部动作。本章讨论工具调用。

本章目标：理解工具是 Agent 的行动接口，并学会设计安全、清晰、可测试的工具。 下一章：学习当工具需要访问大量知识时，如何用 RAG 和记忆组织信息。

工具是什么¶

工具是 Agent 可以调用的外部能力。它可以是：

  • Python 函数。
  • HTTP API。
  • 数据库查询。
  • 文件读写。
  • 搜索引擎。
  • 代码执行环境。
  • 另一个 Agent。
  • 人工审批流程。

从模型视角看，工具是一份 schema：名称、描述、参数和返回值。从工程视角看，工具是一段受控代码，必须有权限、校验、日志和错误处理。

三类工具¶

类型 作用 例子 风险
数据工具 获取上下文 搜索、读数据库、读文件 数据泄露、过期数据
动作工具 改变外部世界 发邮件、退款、改配置 误操作、副作用
编排工具 调用其他能力 调子 Agent、启动任务 调试困难、成本增加

数据工具可以相对宽松，动作工具必须严格控制。凡是会产生真实副作用的工具，都要考虑审批、幂等、回滚和审计。

好工具的标准¶

一个好工具应该像给初级工程师看的函数文档：

  • 名称具体：get_order_status 比 query 好。
  • 描述清楚：说明什么时候用、什么时候不用。
  • 参数少而明确：避免让模型填写复杂嵌套对象。
  • 类型严格：用 JSON schema 或类型系统约束。
  • 返回稳定：返回结构化结果，而不是难解析的长文本。
  • 错误可恢复：错误信息告诉 Agent 下一步该怎么办。
  • 权限最小：只给完成任务必需的能力。
  • 可观测：每次调用有 trace、参数摘要、耗时、结果状态。

工具调用流程¶

用户请求
  -> 模型判断需要工具
  -> 生成 tool_name + arguments
  -> Runtime 校验工具是否存在
  -> 校验参数 schema
  -> 校验权限和审批策略
  -> 执行工具
  -> 记录日志和 trace
  -> 把 observation 返回给模型
  -> 模型继续或结束

关键点：模型只“提出调用”，真正执行必须由 runtime 控制。

错误处理¶

工具失败不可避免。要把失败设计成 Agent 能理解的 observation。

错误 不好的返回 好的返回
参数缺失 Error missing order_id; ask user for order_id
权限不足 403 permission_denied; refund requires human approval
暂时不可用 failed temporary_unavailable; retry_after_seconds=30
找不到记录 null not_found; verify identifier or ask user to confirm

对动作工具，失败时不要让 Agent 猜测是否成功。必须返回明确状态。

MCP 是什么¶

MCP，全称 Model Context Protocol，是一种让 AI 应用连接外部上下文和工具的开放协议。它把“模型需要的资料和能力”标准化成客户端、服务器和协议消息。

核心参与者：

角色 说明
MCP Host AI 应用本体，例如 IDE、桌面助手、Agent 平台
MCP Client Host 内部连接某个 MCP Server 的客户端
MCP Server 暴露工具、资源或提示的服务

MCP 的核心原语：

原语 用途
Tools 可执行函数，让模型采取行动
Resources 可读取上下文，例如文件、数据库记录、文档
Prompts 可复用提示模板或工作流入口

MCP 适合解决“工具和上下文接入标准化”的问题。它不替你决定 Agent 如何规划，也不保证工具安全；安全仍由 Host、Server 和应用策略共同负责。

什么时候用 MCP¶

适合：

  • 你要把同一套工具接给多个 Agent 或多个 AI 应用。
  • 工具来自不同系统，需要标准发现和调用方式。
  • 你希望把文件、数据库、API 以统一协议暴露给模型。
  • 你需要本地工具和远程工具都能接入。

不适合：

  • 只有一个很小的内部函数，直接函数调用更简单。
  • 工具权限、安全边界还没设计清楚。
  • 你只是想让模型多想几步，MCP 不能替代规划。

工具设计反模式¶

  • 一个万能 execute(command) 工具暴露全部权限。
  • 工具描述写得像内部接口文档，模型看不懂使用场景。
  • 参数里要求模型生成复杂 SQL、shell 或代码，却没有沙箱和审计。
  • 动作工具没有人工确认。
  • 工具返回整页 HTML 或超长 JSON，让模型自己找重点。
  • 多个工具名称相似，边界模糊。

本章练习¶

为“差旅预订 Agent”设计工具清单：

  • 查询航班。
  • 查询酒店。
  • 读取公司差旅政策。
  • 创建预订草稿。
  • 提交主管审批。
  • 付款。

对每个工具写出名称、参数、返回值、权限、失败策略，并标记它是数据工具、动作工具还是编排工具。

下一章会讨论知识和记忆：Agent 如何可靠使用大量资料，而不是把所有内容塞进 prompt。
