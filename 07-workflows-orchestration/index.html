07. 工作流与编排¶

上一章讲的是 Agent loop：模型动态决定下一步。本章要处理一个重要工程判断：什么时候应该让模型自主决策，什么时候应该用代码预先定义流程。

本章目标：掌握工作流、Agent 和编排模式的选择。 下一章：当系统需要多个 Agent 或跨系统协作时，再讨论多 Agent 与协议。

工作流与 Agent 的区别¶

维度 工作流 Agent
控制权 代码决定步骤 模型动态决定步骤
可预测性 高 中到低
灵活性 中 高
调试难度 较低 较高
成本和延迟 可估计 随轮数变化
适合任务 步骤明确、规则稳定 开放式、步骤不确定

不要把工作流看成低级方案。很多生产系统应该优先用工作流，因为它更容易测试、审计和解释。

从简单到复杂的模式¶

推荐按复杂度逐级增加：

单次 LLM 调用
  -> RAG
  -> 固定工作流
  -> 工作流 + 少量工具选择
  -> 单 Agent loop
  -> 多 Agent
  -> 跨系统 Agent 协议

只有当前一层无法满足质量、灵活性或维护成本要求时，再上升一层。

常见工作流模式¶

1. Prompt chaining¶

把任务拆成顺序步骤，每一步处理上一步输出。

适合：

  • 先写大纲再写正文。
  • 先抽取字段再生成报告。
  • 先翻译再校对。

优点是可控；缺点是步骤固定，遇到新情况不够灵活。

2. Routing¶

先判断输入类型，再送到不同处理链路。

适合：

  • 客服问题分流：退款、物流、技术支持。
  • 简单问题走小模型，复杂问题走强模型。
  • 不同文档类型走不同抽取规则。

关键是分类要可靠，且每条分支有清晰边界。

3. Parallelization¶

并行执行多个子任务，再汇总结果。

适合：

  • 多角度审查代码。
  • 多资料源搜索。
  • 同一答案生成多个候选后投票。
  • 并行做安全检查和主任务。

风险是结果聚合难，且成本会增加。

4. Orchestrator-workers¶

一个编排器动态拆任务，多个 worker 执行子任务，最后汇总。

适合：

  • 代码仓库大范围修改。
  • 研究报告需要多主题资料。
  • 无法预先知道子任务数量。

这是工作流和 Agent 的中间形态：编排器可以是模型驱动，但系统仍保留较强结构。

5. Evaluator-optimizer¶

一个模型生成，另一个模型评价和反馈，循环优化。

适合：

  • 写作、翻译、报告润色。
  • 代码审查和修复。
  • 有明确评价标准的复杂输出。

关键是评价标准必须具体。没有 rubric 的“再好一点”会变成成本黑洞。

单 Agent 还是多 Agent¶

先最大化单 Agent 能力，再考虑拆分。

考虑多 Agent 的信号：

  • 一个 prompt 里塞了大量条件分支，已经难以维护。
  • 工具太多且相似，模型经常选错。
  • 不同子任务需要完全不同的权限或知识源。
  • 需要不同模型处理不同任务。
  • 需要隔离上下文，避免一个任务污染另一个任务。

不要因为“角色更多看起来更智能”就拆多 Agent。

编排中的人工介入¶

人工介入不是失败，而是 Agent 系统的一部分。适合人工介入的位置：

  • 高风险动作前审批。
  • 资料不足时让用户补充。
  • 连续失败后交接。
  • 低置信度输出审核。
  • 合规、法律、财务、医疗等高风险判断。

系统要能暂停、保存状态、恢复执行，而不是把人工介入当成异常。

本章练习¶

为“供应商安全审查助手”设计三种方案：

  1. 固定工作流方案。
  2. 单 Agent 方案。
  3. 多 Agent 方案。

比较三者在可控性、成本、延迟、调试和上线风险上的差异。

下一章会进入多 Agent 和协议：当 Agent 之间需要协作，应该共享什么，不该共享什么。
