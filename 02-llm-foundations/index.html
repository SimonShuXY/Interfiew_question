02. LLM 基础¶

上一章定义了 Agent：LLM 在循环中控制任务推进。本章聚焦这个“模型大脑”的能力和限制。只有理解 LLM 的输入、输出、上下文和不确定性，才能设计可靠 Agent。

本章目标：掌握 Agent 工程中必须知道的 LLM 基础。 下一章：把这些基础转成提示词与上下文工程。

LLM 的基本工作方式¶

LLM 接收上下文，预测并生成接下来的内容。上下文可以包含：

  • 系统指令：长期约束和角色。
  • 开发者指令：应用层规则、工具使用规则、输出格式。
  • 用户消息：当前任务。
  • 历史消息：多轮上下文。
  • 检索内容：知识库、文件、网页、数据库结果。
  • 工具定义：可调用工具的名称、描述、参数 schema。
  • 工具结果：模型调用工具后返回的 observation。

Agent 的“聪明程度”不只取决于模型，也取决于你给它的上下文是否清晰、相关、可验证。

Token 与上下文窗口¶

Token 是模型处理文本的基本单位，可以粗略理解成词片段。上下文窗口是模型一次能看到的 token 上限。

上下文窗口不是越大越好。大上下文会带来：

  • 成本增加。
  • 延迟增加。
  • 关键信息被噪声淹没。
  • 提示注入风险扩大。

Agent 系统要学会做上下文管理：只放当前任务真正需要的信息，把长文档用检索、摘要、引用和状态压缩管理起来。

温度、确定性与可重复性¶

温度越高，输出越发散；温度越低，输出越稳定。但即使温度很低，LLM 也不是传统确定性函数。Agent 工程不能假设“同样输入永远同样输出”。

因此生产系统需要：

  • 结构化输出 schema。
  • 参数校验。
  • 工具调用前确认。
  • 评测集回归。
  • 失败重试和降级策略。

结构化输出¶

结构化输出要求模型按预期 schema 返回结果，例如 JSON、Pydantic model 或表格字段。这对 Agent 很重要，因为后续代码需要可靠解析模型决策。

适合结构化输出的场景：

  • 分类。
  • 信息抽取。
  • 生成工具参数。
  • 输出任务计划。
  • 返回可机器处理的状态。

不适合只靠自然语言描述再用字符串解析。只要结果要交给程序执行，就应优先使用结构化输出。

工具调用能力¶

工具调用让模型不只是回答，还能选择外部函数。例如搜索、查数据库、计算、写文件、调用业务 API。

工具调用包含三个关键动作：

  1. 模型判断是否需要工具。
  2. 模型生成工具名和参数。
  3. Runtime 校验参数、执行工具、把结果返回给模型。

模型负责选择，代码负责执行和约束。不要让模型直接拥有无限权限。

模型选择¶

选择模型时看五个维度：

维度 问题
能力 是否能稳定推理、遵循指令、调用工具、处理多轮上下文
成本 每次任务平均 token 和工具调用成本是多少
延迟 用户能否接受多轮调用
模态 是否需要文本、图像、音频、视频或代码能力
生态 是否支持结构化输出、函数调用、追踪、评测、权限控制

实践中可以先用强模型建立质量基线，再尝试用更小、更快、更便宜的模型替换部分步骤。不要一开始就用便宜模型判断方案不可行。

LLM 的典型失败模式¶

失败模式 表现 工程缓解
幻觉 编造事实、API、引用 RAG、引用校验、工具查询
指令漂移 多轮后忘记约束 状态摘要、系统规则、回归测试
参数错误 工具参数缺失或格式错 JSON schema、类型校验、重试
过度行动 不该调用工具也调用 权限、审批、工具描述优化
上下文污染 被恶意文档影响 输入隔离、提示注入检测、最小上下文
循环 反复调用同一工具 最大轮数、预算、重复检测
