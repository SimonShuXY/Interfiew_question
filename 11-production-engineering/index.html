11. 生产化工程¶

上一章讨论了安全。本章把 Agent 当成真实软件系统来设计：它需要部署、状态管理、异步执行、监控、成本控制、版本管理和故障恢复。

本章目标：建立生产级 Agent 的工程架构视图。 下一章：在理解工程要求后，选择合适框架。

生产架构分层¶

一个生产 Agent 系统通常包含：

用户入口
  -> API / Session 服务
  -> Agent Runtime
  -> Tool Gateway
  -> 数据与知识层
  -> 评测与观测系统
  -> 权限、审计、人工审批
层 职责
用户入口 Web、App、Slack、IDE、语音
API / Session 鉴权、会话、限流、任务 ID
Agent Runtime 运行 loop、调用模型、管理状态
Tool Gateway 工具注册、参数校验、权限、超时
数据层 RAG、数据库、对象存储、记忆
观测层 trace、日志、指标、用户反馈
安全层 策略、审批、审计、脱敏

不要把所有逻辑塞进一个 prompt 或一个脚本里。

状态与会话¶

Agent 状态要可恢复。至少要保存：

  • session_id。
  • task_id。
  • 用户目标。
  • 当前步骤。
  • 已确认事实。
  • 工具调用历史摘要。
  • 关键中间产物引用。
  • 等待用户或人工审批的状态。
  • prompt、模型、工具版本。

长任务不要只依赖内存。服务重启后应能从 checkpoint 恢复或给出清晰失败说明。

异步与长任务¶

Agent 常常需要多步搜索、文件处理、代码执行或人工审批。长任务建议采用：

  • 任务队列。
  • 状态机。
  • 流式进度。
  • 可取消任务。
  • 超时和预算。
  • 断点恢复。
  • 用户通知。

同步 HTTP 请求适合短任务；长任务应返回 task_id，让前端轮询、订阅或接收推送。

工具网关¶

Tool Gateway 是生产 Agent 的关键组件。它负责：

  • 工具发现和注册。
  • 参数 schema 校验。
  • 用户与 Agent 权限校验。
  • 审批策略。
  • 超时、重试、熔断。
  • 返回值脱敏。
  • 调用日志。
  • 幂等键。

这样做能把模型的不确定性隔离在可控执行层之外。

版本管理¶

Agent 行为由多个版本共同决定：

  • 模型版本。
  • prompt 版本。
  • 工具 schema 版本。
  • RAG 索引版本。
  • 业务规则版本。
  • 代码版本。
  • 评测集版本。

上线问题定位时，要能回答：“这个错误是在什么模型、什么 prompt、什么工具版本、什么知识库版本下发生的？”

成本与延迟¶

Agent 成本来自：

  • 多轮模型调用。
  • 大上下文 token。
  • 检索和重排。
  • 工具调用。
  • 并行或多 Agent。
  • 失败重试。

优化顺序：

  1. 减少无意义轮数。
  2. 缩短上下文。
  3. 缓存稳定资料和工具结果。
  4. 用小模型处理简单步骤。
  5. 并行只用在真正可并行的步骤。
  6. 对高成本任务设置预算和用户确认。

可靠性设计¶

常见故障和缓解：

故障 缓解
模型超时 重试、降级模型、返回可恢复状态
工具失败 错误分类、重试、熔断、替代工具
输出格式错误 schema 校验、自动修复、失败返回
RAG 无结果 告知资料不足、扩大检索、询问用户
循环调用 最大轮数、重复检测、预算
人工审批未响应 暂停任务、提醒、超时取消

可靠系统不是永远不失败，而是失败可见、可解释、可恢复。

生产就绪清单¶

上线前至少确认：

  • 有离线评测集。
  • 有 trace 和关键指标。
  • 有最大轮数、超时、成本预算。
  • 动作工具有权限和审批。
  • 敏感数据脱敏。
  • RAG 有引用和权限过滤。
  • prompt、工具、模型版本可追踪。
  • 用户能知道 Agent 做了什么关键动作。
  • 失败时能交给人工或给出恢复方式。

本章练习¶

画出“合同审查 Agent”的生产架构图，标出：

  • 哪些服务处理用户请求。
  • Agent runtime 保存哪些状态。
  • 工具网关管理哪些工具。
  • 文档如何进入 RAG。
  • 审批在哪些节点发生。
  • trace 如何贯穿整次任务。

下一章会比较主流框架，帮助你把这些工程要求映射到实际技术选型。
