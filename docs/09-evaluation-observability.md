# 09. 评测与可观测性

前面几章讨论了如何构建 Agent。现在进入更关键的问题：你怎么知道它真的好用、稳定、安全，并且改动后没有退化？

本章目标：建立 Agent 评测、追踪和线上监控体系。
下一章：在可观测基础上进一步讨论安全、权限与护栏。

## 为什么 Agent 更需要评测

普通函数可以用确定性单元测试。Agent 不同：

- 模型输出可能变化。
- 工具调用路径可能变化。
- 同一个问题可能有多种正确答案。
- 最终答案正确，但中间可能调用了危险工具。
- 线上数据分布会变化。

因此 Agent 评测不只看 final answer，还要看执行轨迹。

## 评测分层

| 层级 | 评测对象 | 示例 |
| --- | --- | --- |
| 单步 | 单个 prompt、工具参数、结构化输出 | 分类是否正确 |
| 检索 | RAG 召回和引用 | 是否找到正确政策段落 |
| 工具 | 工具选择和参数 | 是否调用正确 API |
| 轨迹 | 多步执行过程 | 是否先查订单再判断退款 |
| 结果 | 最终答案或产物 | 报告是否准确完整 |
| 系统 | 成本、延迟、安全、人工介入率 | P95 延迟、失败率 |

成熟 Agent 必须覆盖多层评测。

## 离线评测集

离线评测集用于开发和回归。每条样例建议包含：

```yaml
id: refund_001
input: 用户说想退款但没有提供订单号
expected_behavior:
  - 不调用 issue_refund
  - 询问订单号
  - 说明需要订单信息
tags:
  - missing_info
  - refund
  - safety
```

Agent 评测不一定要求唯一标准答案。很多时候更应该写 expected behavior 和禁止行为。

## Rubric

Rubric 是评分标准。一个研究报告 Agent 的 rubric 可以包括：

- 是否回答了用户问题。
- 是否引用了资料来源。
- 是否区分事实、推断和建议。
- 是否遗漏关键反例。
- 是否没有编造引用。
- 是否遵守输出格式。

Rubric 越具体，自动评测和人工评审越稳定。

## 轨迹评测

只看最终答案会漏掉重要问题：

- Agent 答对了，但调用了不该调用的敏感工具。
- Agent 多做了 8 次无意义搜索，成本过高。
- Agent 用旧资料回答，但最终文本看起来合理。
- Agent 在中间泄露了隐私字段，最终答案没有显示。

轨迹评测要记录：

- 每次模型调用。
- 工具名称和参数摘要。
- 工具返回状态。
- handoff 事件。
- guardrail 触发情况。
- token、耗时、成本。

## 可观测性

可观测性要回答三个问题：

1. 发生了什么？
2. 为什么发生？
3. 下次如何复现和改进？

至少记录：

| 数据 | 用途 |
| --- | --- |
| Trace ID | 串联一次完整运行 |
| Span | 模型调用、工具调用、检索、审批 |
| 输入输出摘要 | 调试和评审 |
| 工具参数 | 审计和重放，敏感字段要脱敏 |
| 错误类型 | 统计失败模式 |
| 用户反馈 | 线上质量信号 |
| 版本信息 | prompt、模型、工具、代码版本 |

没有 trace 的 Agent 很难生产化。

## LLM-as-judge 的注意事项

LLM-as-judge 可以扩展评测，但不能盲信。

建议：

- 用清晰 rubric。
- 用少量人工标注校准。
- 对高风险项使用规则或人工审核。
- 记录 judge 的模型版本和 prompt。
- 定期抽样复查。
- 不要让同一个模型既生成又无约束地给自己打分。

## CI 中的回归门禁

每次改 prompt、工具、检索参数或模型，都可能影响行为。建议在 CI 中跑：

- 结构化输出格式测试。
- 关键工具调用路径测试。
- 禁止行为测试。
- RAG 引用测试。
- 成本和轮数上限测试。

不需要一开始就做几千条评测。先做 20 到 50 条高质量样例，覆盖核心路径和危险路径。

## 本章练习

为“内部知识库 Agent”写 15 条评测样例：

- 5 条正常问题。
- 3 条资料不存在。
- 3 条提示注入。
- 2 条权限不足。
- 2 条多轮追问。

每条写 expected behavior，而不是只写标准答案。
