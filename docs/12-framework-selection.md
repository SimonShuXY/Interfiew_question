# 12. 框架选型

上一章给出了生产级 Agent 的工程要求。本章讨论如何选框架。框架不能替代架构判断，但能帮你更快处理模型调用、工具 schema、状态、追踪、工作流和多 Agent。

本章目标：建立选型标准，而不是追逐框架热度。
下一章：用综合项目把前面知识串起来。

## 先问三个问题

选框架前先问：

1. 我的任务是固定流程，还是开放式多步决策？
2. 我的核心难点是工具、RAG、工作流、多 Agent、观测，还是部署？
3. 我需要掌控底层 loop，还是希望 runtime 帮我管理？

如果你还答不清楚，先用最小代码实现一版，不要马上引入大型框架。

## 选型维度

| 维度 | 需要确认 |
| --- | --- |
| 模型支持 | 是否支持你要用的模型和结构化输出 |
| 工具系统 | 是否易于定义、校验、审批和追踪工具 |
| 状态管理 | 是否支持 session、checkpoint、长期任务 |
| 工作流 | 是否支持图、条件分支、并行、人工介入 |
| RAG | 是否内置数据加载、索引、检索、重排 |
| 多 Agent | 是否支持 manager、handoff、团队或远程 Agent |
| 观测评测 | 是否有 trace、eval、debug UI 或生态集成 |
| 部署 | 是否适合你的云、语言、团队栈 |
| 可逃逸性 | 遇到问题时能否下探到底层 API |

## 主流框架速览

| 框架/生态 | 核心优势 | 适合场景 | 注意点 |
| --- | --- | --- | --- |
| 直接使用模型 API | 透明、可控、依赖少 | 简单工具调用、原型、深度定制 | 自己实现 loop、状态、追踪 |
| OpenAI Agents SDK | Agent、工具、handoff、guardrails、sessions、tracing 集成 | 基于 OpenAI 模型或兼容生态快速构建 Agent | 与具体 SDK 版本强相关，需跟官方文档 |
| LangChain / LangGraph | Agent runtime、图执行、持久化、人机协作、生态丰富 | 复杂工作流、可恢复图、多模型工具链 | 抽象多，团队要理解底层状态图 |
| LlamaIndex | RAG、数据连接、索引、Agentic RAG 强 | 知识库、文档、检索增强 Agent | 非 RAG 场景可能不需要完整能力 |
| Microsoft Agent Framework | Agents、Harness、Workflows、企业特性、类型安全、MCP | .NET/Python/Go、企业系统、Azure/Microsoft 生态 | 注意不同语言能力成熟度 |
| AutoGen / Semantic Kernel 存量项目 | 多 Agent 和企业编排历史生态 | 维护已有系统或迁移项目 | 新项目需关注 Microsoft Agent Framework 的继任关系 |

其他框架也可能适合特定场景。由于生态更新很快，新增框架前请阅读其最新官方文档、版本说明和生产案例。

## 自研还是用框架

适合自研：

- 需求很窄，只需要少量工具调用。
- 对 trace、权限、部署有强定制要求。
- 团队希望完全掌控 prompt 和 loop。
- 框架抽象反而阻碍调试。

适合框架：

- 需要快速搭建多步 Agent。
- 需要标准工具、handoff、session、tracing。
- 需要图工作流、checkpoint、人机协作。
- 需要丰富 RAG 数据连接器。
- 团队愿意接受框架约束换开发效率。

## 推荐决策流程

```text
能用普通函数解决？
  是 -> 写函数
  否 -> 能用单次 LLM 或 RAG？
      是 -> 不上 Agent
      否 -> 步骤是否稳定？
          是 -> 工作流
          否 -> 单 Agent
              单 Agent 是否因职责/工具/权限过载而失败？
                  是 -> 多 Agent
                  否 -> 保持单 Agent
```

框架选择也按这个流程：需求越明确，越可以用简单代码；需求越复杂，越需要 runtime、工作流和观测支持。
